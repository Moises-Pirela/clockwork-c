# Clockwork C

A small C11 game engine built around a standalone ECS (`include/clockwork.h`, a port of the core of Exmortalis' `engine/ECS/clockwork`), with the pieces needed to make *several games from one engine* the way Unity or Godot do: a **game module** contract, **reflection** over components, a **text scene format**, a **launcher** that creates and lists projects, a standalone **editor** executable that opens a project, places entities, edits every component field, lays out the game's **interface** (anchored, resolution-independent menus and HUDs), saves and loads scenes, plays the scene in place and builds the game, and a generic **player** that runs any module on any scene (and becomes the exported game when the module is linked in).

```
include/clockwork.h     ECS core: worlds, components, queries, observers, commands, snapshots, sim, clock
include/cw_reflect.h    component reflection: fields, ranges, labels, semantics; generic codec; value access
include/cw_scene.h      text scene format, reflection-driven, human-readable, tolerant of schema growth
include/cw_assets.h     the project's asset registry: import, scan, ids (hash of the name), @name references from components
include/cw_anim.h       keyframe clips over reflected fields; the engine's Animation component and system
include/cw_ui.h         a game's interface as entities: anchored rectangles, images, text, buttons; resolution-independent layout
include/cw_game.h       the game module ABI (components, systems, prefabs, canvas drawing), loading, bound worlds, projects
src/                    the engine
render2d/               the 2D renderer on Sokol (window, camera, drawing, picking, UI, lights, post-processing, images, materials, sprites)
runtime/                host side: the player (clockwork_player), the render2d canvas modules draw through, shared widgets, the dock layer
launcher/               the launcher (clockwork_launcher): project registry, creation from a starter template, open/run/build
editor/                 the editor (clockwork_editor): a headless document model plus a render2d window
games/combat/           a game: combat_game.c (module), combat.cwproj (project), scenes/*.cwscene
games/orbit/            a second, unrelated game, to prove the tools are generic
tools/build-game.sh     builds a project's module (shared library) or exports a standalone game; the editor calls it
tests/                  engine, game-layer and editor checks, all headless
```

The engine never includes game code and the games never include renderer or editor code. A game is one C file that registers its components **with reflection** (`cw_reflect_register`), its systems, the prefabs an editor can place, and how its entities draw through a `cw_canvas` of function pointers the host supplies. It is compiled into a shared library (`games/<name>/build/<name>_game.so|.dylib|.dll`) that the editor and the player `dlopen`/`LoadLibrary`, or linked statically into an exported game. The ECS is the only state: the editor edits a `cw_world` bound to the module (`cw_game_world`), the inspector walks the `cw_type_info` the world carries for every registered component, scenes are the world written field by field, and play mode simply runs the module's systems on that same world.

## Build

Linux (`gcc` or `clang`; only the X11/GL *runtime* libraries are needed, the headers are bundled):

```sh
./build.sh                 # debug; --release, --sanitize (ASan/UBSan), --no-gui, --compiler clang
build/gcc-debug/clockwork_launcher                                        # create, list and open projects
build/gcc-debug/clockwork_editor --project games/combat/combat.cwproj     # or straight into the editor
build/gcc-debug/clockwork_player --project games/orbit/orbit.cwproj      # or run a game
```

Each run compiles the engine, both game modules (at the paths their projects name), runs every headless check (engine, game layer through the module linked statically *and* loaded as a shared library, the editor document including a real build-and-hot-reload through `tools/build-game.sh`, the launcher including creating and building a project from the template, render2d math, particles/effects, post-process config, and the player on both projects), then builds the player, the editor and the launcher. Note that game modules are built into their project directories whatever the configuration, so a `--sanitize` run leaves sanitized modules there until the next plain build.

CMake (any C11 toolchain; Windows uses Direct3D 11, macOS Metal, Linux OpenGL):

```sh
cmake -S . -B build/cmake -DCMAKE_BUILD_TYPE=Debug
cmake --build build/cmake
ctest --test-dir build/cmake --output-on-failure
build/cmake/clockwork_editor games/combat/combat.cwproj
```

`-DCW_BUILD_GUI=OFF` skips the Sokol tools, `-DCW_BUILD_GAMES=OFF` the modules. `build.ps1` (Visual Studio C++ Build Tools) and `build-macos.sh` (Xcode Command Line Tools) mirror `build.sh`; this revision's Windows and macOS paths are written to match but were exercised on Linux only. The ECS library itself needs nothing but a C11 compiler; the game-module loader needs `dlopen` (`-ldl`, automatic in the scripts and CMake) or `LoadLibrary`.

The platform layer uses `VirtualAlloc` on Windows and `mmap`/`mprotect` on POSIX. The virtual address reservation is intended for 64-bit processes.

## The launcher

`clockwork_launcher [--engine ROOT]` is the front door. Its panels (projects, project details, new project, build log) are dockable tabs like the editor's, with their own saved layout (`launcher_layout.cfg`) and a `reset layout` button. It lists every project it knows, most recently opened first, with its state (module built or not, how many scenes, last change), and for the selected one offers *open in editor*, *run*, *build*/*rebuild* (with the compiler output in a log panel) and *remove from list*, plus *edit* and *play* per scene. Double-click or Enter opens the editor; Ctrl+N starts a new project.

**New project**: a name (`[A-Za-z][A-Za-z0-9_]*`) and a parent directory (default `games/`) produce `<dir>/<name>/<name>.cwproj`, `<name>_game.c` and `scenes/main.cwscene`, from `launcher/template/`: a complete starter game (Position, Shape and Mover components with reflection, a bouncing system, two prefabs, drawing and descriptions) that the launcher then builds, so the project opens in the editor ready to place things. The rest of the template directory is copied as it is: a starter image (`assets/images/ball.png`), a material that uses it (`materials/ball.cwmat`, glow effect) which the scene's ball shows through the engine's `Sprite` component, a `rounded` button material (`materials/button.cwmat`) on the scene's button, and a `render.cfg` that starts the game unlit (lights and fog off until the game places lights). The scene also carries a small interface - a title and a *bounce* button in the top right corner that the game's `interface` system answers by reversing every mover - as the pattern for menus and HUDs. The template itself is compiled as a module by the build to keep it honest.

The registry is `<engine_root>/projects.cwlist` (`CW_PROJECTS` overrides): one absolute `.cwproj` path per line. Projects under `games/` are registered automatically; *add existing* registers any `.cwproj` by path; a project whose file no longer parses stays listed with its error so it can be fixed or removed. The editor and the player are expected next to the launcher (`CW_EDITOR` / `CW_PLAYER` override). `launcher/launcher_core.h` is the window-free model; `tests/test_launcher.c` drives it, including creating a project from the template, building it through the script and loading its scene through the engine.

## The editor

`clockwork_editor [--project game.cwproj] [--scene file.cwscene] [--engine ROOT]` is a separate program, not a mode of any game. It opens a **project** (`*.cwproj`: the game's name, the module library path, the sources that make it, the scenes directory and the main scene), loads the module, binds a fresh world to it and opens the main scene.

- **Docking.** Every panel is a tab in a dock space (`runtime/host_dock.h`): drag a tab onto the middle of another panel to group them, onto an edge to split that panel (a translucent preview shows where it will land), drag the gutters to resize, close with the x, reopen from the `panels` menu, `reset layout` to go back to the default (scene/assets/world left, viewport in the middle, inspector/project/rendering/preferences right, build log below when open). The layout is saved per user (`editor_layout.cfg` next to the preferences) and restored on start. The dock layer is plain C on render2d's immediate-mode UI: Dear ImGui's docking branch would have needed a C++ dependency and network access that this tree does not have, so the same behaviour was implemented in ~450 lines and covered by `tests/test_dock.c` (tree operations, persistence, and scripted mouse sessions for tab clicks, tab drags to edges and centres, splitter drags and closing, with render2d stubbed).
- **Config and runtime components.** A module can declare a type as *config* (`CW_CONFIG_TYPE`: authored in the inspector and scenes, with a `generates` name and a `bake` function) and the type it generates as *runtime* (`CW_RUNTIME_TYPE`: never written to scenes, saved in snapshots, read-only in the editor). The engine registers a `cw_bake` system first in `CW_ENTITY_CREATED` that runs each config component's bake when an entity enters a running world (`cw_reflect_bake`; an existing runtime component is never overwritten, so a loaded save game keeps its state). The editor keeps baking off while editing - units carry `HealthConfig`, nothing else - and turns it on when play starts (`cw_game_world_bake_all`), so `Health` appears with its `current` at full, drains during play, and is gone again on stop because the scene never contained it; the inspector colours the headers (`HealthConfig  config -> Health`, `Health  runtime (generated)`), renders runtime fields read-only, and keeps runtime types out of the add menu; the world panel shows the pairs and the baking state. The player bakes on load. `games/combat` uses it for health (`HealthConfig.maximum` -> `Health {current, maximum}`).
- **Animation** (panel, below the viewport by default): a keyframe animation editor for gameplay entities. A clip (`animations/<name>.cwanim`, an `animation` asset) holds tracks, each animating one field of one component by name (`Light.intensity`, `Position.y`, `Shape.radius`, ...) with keys (time, value, interpolation: linear, step, smooth ease, ease in, ease out) - so any reflected numeric, bool, enum or flags field of any game is animatable, and a clip works on every entity that carries those components. Select an entity, *new* a clip (or open one from the list), *+ track* offers the entity's animatable fields, *+key* on a track sets a key at the playhead from the entity's current value; click keys to edit their time, value and interpolation, drag them to retime (snapping to the ruler step when grid snapping is on), scrub by clicking the ruler or a lane, *play/pause/stop* preview the clip on the entity in place with once/loop/pingpong modes and a length field. Previewing never changes the scene: the components a clip touches are saved when the preview starts and restored when it stops. **Record** turns inspector edits into keys at the playhead (auto-creating tracks) and keeps those edits out of the scene history. Clips are assets; to play one in the game add the engine's **`Animation`** component to the entity (every bound world has it, registered after the module's components) and pick the clip: `clip` (asset), `speed`, `playing`, `mode` override; the engine's `cw_anim` system advances it every tick and applies the clip through reflection (`cw_anim_step`), loading clips from the project's assets into a per-world cache - in play mode, in the player and in exported games alike.
- **Creating entities and prefabs.** `E` (or the palette's *new empty entity*) places an entity that carries only the game's position component; components are then added from the inspector's *add component* list, each with its type's defaults. The inspector's *save as a prefab* writes the selection - one entity or several, with their components, names and the references between them - as a scene fragment to `prefabs/<name>.cwprefab`, registered as a prefab asset; project prefabs appear in the palette under *project prefabs* next to the module's, placing one instantiates copies with fresh ids (references remapped, the first saved entity is the anchor at the click, `cw_scene_instantiate`), saving again under the same name updates it, and the assets panel deletes it. Instances keep no link to their prefab.
- **Palette** (scene panel): one button per prefab the module exports, grouped by category; keys 1-9 pick the first nine. Click in the level to place (shift keeps the tool). Prefabs are the module's spawn functions, so what they create and where they clamp is the game's business.
- **Materials and sprites** (material panel, next to the animation panel): textured entities without game drawing code. An **image** asset (PNG - decoded by the engine's own inflate, no zlib - TGA, PPM/PGM; `render2d/r2d_image.h`) becomes a GPU texture on demand; a **material** (`materials/<name>.cwmat`, a text asset: `render2d/r2d_material.h`) names the texture, an **effect** with its parameters, a blend mode (alpha, additive, multiply, opaque), sampling (linear/nearest, clamp/repeat), a tint and uv tiling/offset. The built-in effects are one uber shader (one shared body in the HLSL dialect with a GLSL, an HLSL and an MSL preamble, so every effect runs on every backend): plain sprite, flash (hit feedback), outline, dissolve (noise burn with a glowing edge), hue/saturation/brightness, wave, pixelate, glow, and six **interface effects** that read the quad's pixel size and the element's state: *rounded* (signed-distance corners and a border that stay crisp at any size, brightens on hover, sinks when pressed), *gradient* (two tints along an angle, scrolling or mirrored), *sweep* (a band of light crossing the element, brighter while hovered), *ring* (a radial progress arc from the element's fill over a track colour), *pulse* (a glowing border that breathes and flares on hover) and *scanlines* (scrolling CRT lines with flicker and a hover tint). **Custom** takes a **shader** asset (`shaders/<name>.cwshader`): a GLSL function `vec4 material(vec4 base, vec2 uv, vec4 p0, vec4 p1, vec4 p2, vec4 p3, float time)` that render2d wraps into a full program (OpenGL backend; D3D11 and Metal fall back to the plain sprite effect) with, in scope, `tex`, `texel`, `size` (the quad in pixels), `state` (the element's hover and press eased to 0..1 by the engine, its fill, and the seconds since its state changed), `elem` (the element's own four parameters, `UiImage.param_x..w`, animatable like any field) and the helpers `hash2`, `vnoise`, `hue_shift`, `rounded_box` and `angle01`. The panel lists the project's materials, edits every property with a live preview (the material is drawn through the same sprite path as the game): as a *sprite* on a checkerboard, or as an *element* - a button-sized quad and a square that react to the mouse over them and cycle their fill, so hover glows, press states and progress rings are seen without running the game. *new* writes a shader from one of the **starters** (*rim*, *button*: rounded gradient with a rim and hover/press response, *ring*: a progress ring with a bright tip, *shine*: a sweeping highlight sped up by `elem.x`, *hologram*: scanlines, flicker and a breathing edge, *bar*: a health bar that slides from green to red with animated stripes), compile errors show with the asset's own line numbers, and saving a shader from any text editor recompiles it (the file is watched). Entities show a material through the engine's **`Sprite`** component (registered in every bound world after the module's types, like `Animation`): `material` (a material asset, picked from the project's materials), `width`/`height`, `rotation`, `layer`, `flip_x`/`flip_y`, a colour, and `columns`/`rows`/`frame` for sprite sheets; `cw_game_world_draw` draws it after the module at the entity's `CW_SEM_POSITION` through `canvas->sprite`, in the editor, the player and exports alike, registers a pick area, and shows a magenta placeholder when the material or its texture is missing. Asset pickers are filtered by the field's name (`material` -> materials, `sprite`/`image`/`texture` -> images, `clip` -> animations, `sound` -> audio, ...: `cw_asset_type_for_field`).
- **Interface** (the `interface` group of the scene panel, the game view and the inspector): menus and HUDs that scale to any screen, built the way Unity's canvas works. An interface element is an entity with the engine's **`UiRect`** component (registered in every bound world, like `Sprite`): a parent (another element, or the canvas), two **anchors** as fractions of the parent's rectangle and pixel **offsets** from them (`left`/`top`/`right`/`bottom`), so equal anchors pin a fixed-size element to a corner or the centre and different anchors stretch it with its parent; plus `order` among siblings and `visible`. **`UiImage`** fills the rect with a material asset or a flat colour, optionally nine-sliced (`border`, so frames keep their corners at any size) or partially filled (`fill_mode`/`fill`: health bars), and hands its material's shader the element's size, eased hover/press, fill and its own `param_x..w` (so one `rounded` or `pulse` material makes every button it is on react to the mouse, and a `ring` material turns any square element into a progress dial driven by `fill`); **`UiText`** is a line of text (a string field, quoted in scenes) with a size, colour and alignment; **`UiButton`** makes an element clickable (hover and press tints, an `action` number, `enabled`). The engine lays every element out (`cw_ui_layout_all`, into the transient `UiLayout`: window and reference rectangles, never saved), draws them after the module through the canvas's `hud_image`/`hud_text` ops, and runs the `cw_ui` system before the module's so buttons see the mouse the host fed: game code asks `cw_game_ui_clicked(world, action)` or `cw_ui_clicked(world, &gw->ui, id)` and writes texts with `cw_ui_set_textf` (combat's scoreboard system fills the HUD's `UiText`s that carry its `Scoreboard` component; the starter template's *bounce* button reverses the movers). **Resolution**: offsets are *reference pixels*; the project names the resolution the interface was designed for and how it scales when the window differs (`ui 1280 720 expand` in the `.cwproj`, edited in the project panel: *expand* keeps the whole design visible - the scale is the smaller of the width and height ratios - *shrink* fills, *width*/*height* follow one axis, *pixels* never scales). The root rectangle is the window divided by that scale, so anchored elements spread with the aspect ratio while sizes scale uniformly: a bar stretched across the top stays across the top on an ultra-wide monitor or a phone, a button in a corner stays in the corner at the same relative size. In the editor, the palette's *panel*, *image*, *text*, *button* (an image with a stretched label child) and *bar* create elements centred in the selected element (or the canvas); click and drag moves them (children follow; a selected element keeps the mouse even where its label sits on top, ctrl-click reaches the element on top), the eight handles resize, arrows nudge, Ctrl+D duplicates 16 pixels aside; the inspector's `UiRect` section has the nine anchor presets and the three stretches (changing anchors never moves the element), the element's reference size and position, and re-parenting (*to canvas*, or into the second selected element) that keeps the screen position; the yellow triangles show where the anchors sit on the parent. The toolbar's *view* cycles a resolution preset (1280x720, 1920x1080, 800x600, a 1080x1920 portrait, a 2560x1080 ultra-wide, or the free viewport) letterboxed into the viewport, with the scale it implies, so the layout can be checked on every aspect ratio without leaving the editor; in play mode the interface is live (buttons react) instead of editable. The player lays the interface out on its window and feeds it the mouse; exports do the same.
- **Viewport**: the module draws the world exactly as the player would (with `editing` set, so it may add gizmos and labels); the editor overlays the level bounds, a grid (G), hover and selection rings around everything the module declared pickable, and a generic ring for any positioned entity the module did not draw. Click, shift-click and box-drag select; drag moves the selection; arrows nudge (shift x10); Del deletes; Ctrl+D duplicates (entity references between duplicated entities are remapped through reflection); Ctrl+A selects all. Right/middle drag pans, the wheel zooms, F refits. L previews the game's lighting and post-process stack.
- **Scenes** (left): the `*.cwscene` files in the project, click to open (a second click confirms discarding unsaved edits); a name field and *save as* write a new one; Ctrl+S saves, Ctrl+N starts an empty scene.
- **Entities** (left): every entity with its display name or the module's description; click selects, shift-click toggles.
- **Inspector** (right): the selected entity's name (stored in the scene, not in the world) and, for every non-transient component it carries, every field the module described: text boxes with -/+ steppers for numbers and entity references, cycling buttons for enums, one toggle per flag bit, angles shown in degrees. Values are validated by the field ranges and the type's `validate` callback before they reach the world, so the inspector cannot produce a component the game would reject. Components can be removed (x) and added from the list of the module's non-transient types, with the type's defaults.
- **Undo/redo** (Ctrl+Z / Ctrl+Y) of every operation, snapshot-based: after each edit the scene is written to text and kept; undo reloads the previous image into the same world, so entity ids, references and the selection survive.
- **Play** (F5 or the toolbar) runs the module's systems on the scene in place at the module's tick rate; Space pauses, N steps one tick, Escape/F5 stops and restores the scene from the image taken when play started. Entities placed or moved while playing are discarded on stop and never recorded in the history.
- **Assets** (panel): the project's asset browser. Every file that belongs to the project is registered in `assets.cwassets` with a type (scene, image, audio, font, data, config, source, prefab, animation, material, shader, other - by extension), a unique name and its path relative to the project; scenes and sources are registered by a scan when the project opens. Import by typing a file or directory path, or by **dropping files onto the editor window**: the file is copied into `assets/<type>/` (data under `assets/data`, images under `assets/images`...) and registered; re-importing is refused unless replaced. Filter by type, select an asset for its details (size, id, path, how many components reference it), rename it (the id is the hash of the name, so references by the old name stop resolving), forget it or delete the file; scenes open from here. Components reference assets through a `uint32_t` field with `CW_SEM_ASSET`: the inspector shows a picker over the project's assets, scenes store `sprite=@hero.png`, and game code resolves the id with `cw_assets_path(cw_assets_of(world), id, ...)` against the registry the host attached to the world (the starter template's `Shape.sprite` shows the pattern). The player loads the manifest with the project.
- **World** (panel): the ECS as it is right now. The module (name, scene version, tick rate, prefabs, bounds), the world (entities, tick, id allocator, pending destructions, memory, cached queries), every registered component with the number of entities carrying it (transient and opaque ones marked; click selects the carriers), and every system in dispatch order with its phases, order and authority - click toggles it, which is the quickest way to see what a system does while playing.
- A prefab asset's details offer *place*; the type filter has a *prefab* entry.
- **Settings** are three panels (F10 / the toolbar focus them). *Project*: the player's window size and title (saved into the `.cwproj`) and the project's files. *Rendering*: the project's rendering settings (below). *Editor*: the user's own preferences - text scale, grid and its spacing, snapping (placement, drags and nudges snap to the grid), nudge step, rendering preview on start, wheel zoom step, confirming discards, opening the main scene on start, autosave (a `<scene>.autosave.cwscene` copy every N seconds while dirty; never the scene itself) - described by a tunables table like the rendering settings (`editor/editor_settings.h`) and saved per user to `CW_EDITOR_CONFIG`, else `~/.config/clockwork/editor.cfg` (`%APPDATA%\clockwork\editor.cfg` on Windows).
- **Rendering settings** (the rendering panel) are the project's look: every render2d tunable (post-process stack on/off, HDR, render scale, pass order, lighting, fog, bloom, depth of field, motion blur, chromatic aberration, tone mapping, vignette, shake, quality tiers), one tab per section, generated from the tunables table (`render2d/r2d_tunables.h`) so new tunables appear without editor changes; numbers have text boxes and -/+ steppers, enums cycle, booleans toggle, strings (the pass order) are edited inline. Changes apply live in the viewport (the *preview*/L toggle shows the game's look or a plain view, through `r2d_post_set_bypass`, without touching the values) and *save* writes the project's render file (`render render.cfg` in the project, `<project>/render.cfg` by default); *reload* and *defaults* do what they say, edits made to the file outside the editor are picked up automatically, and the toolbar button shows `settings*` while unsaved. The player loads the project's render file when it exists (else the engine's `tunable.cfg` next to the binary; `--config` overrides), and exports copy it next to the game, so rendering settings are a project asset like scenes.
- **Build** (F7) runs `tools/build-game.sh <engine> <project> module ...` with the project's sources, shows the compiler output in the log panel (`), and on success **reloads the module** while keeping the scene (unknown components or fields of the new schema are dropped with a warning). **Export** (F8) runs the same script in `export` mode: a standalone executable (`games/<name>/build/<name>`) made of the player with the module linked in, next to a copy of the project as `game.cwproj`, its scenes, its render settings and its assets (the manifest and every file it lists - images, materials, shaders, clips, prefabs - at the same relative paths); it runs without the editor or the engine tree. **Run** (F9) saves and launches `clockwork_player` on the current scene. The engine root comes from `--engine`, `CW_ENGINE_ROOT` in the environment, or the path compiled in by the build; the player path from `CW_PLAYER` or the editor's own directory.

Everything above is a call into `editor/editor_core.h`, which knows nothing about windows; `tests/test_editor.c` drives it headlessly through opening a project, placing, moving, duplicating, editing fields, adding/removing components, undo/redo, saving/listing/loading scenes, play mode, building and hot-reloading the module, and switching to a second project.

## Writing a game module

A module is a translation unit that defines `cw_game_export()` returning a `cw_game_module` (see `include/cw_game.h`; `games/orbit/orbit_game.c` is a 200-line complete example, `games/combat/combat_game.c` a fuller one):

1. **Components with reflection.** Describe each component with a `cw_type_info`: fields (`CW_FIELD`, `CW_FIELD_RANGE`, `CW_FIELD_NAMED` for enums and flags, `CW_FIELD_STR` for fixed-capacity strings, `CW_FIELD_SEM` for semantics such as `CW_SEM_POSITION_X/Y`, `CW_SEM_RADIUS`, `CW_SEM_ANGLE`, colour channels, `CW_SEM_ASSET` for asset references, or `CW_SEM_RUNTIME` for state that is saved but not shown), optional defaults, an optional `validate` callback for cross-field invariants, and flags: `CW_TYPE_TRANSIENT` for runtime-only state (never saved, never offered in the editor), `CW_TYPE_INTERNAL` (saved but hidden), `CW_TYPE_CONFIG` with `generates` and `bake` (authoring data that produces a runtime component), `CW_TYPE_RUNTIME` (generated; in snapshots, not scenes). `register_components` calls `cw_reflect_register` for each, which registers the component in the world, attaches the description, marks transients and installs the **generic codec** (little-endian, validated on load) so binary snapshots need no hand-written marshalling either.
2. **Systems**: `register_systems` registers ordinary `cw_system_desc`s.
3. **Per-world state**: optional `bind`/`unbind` attach whatever the systems need to `world->user` (scratch buffers, statistics).
4. **Prefabs**: `{name, category, spawn}`; `spawn` fills the components of a freshly created entity at a position.
5. **Drawing**: `draw(world, canvas, ctx)` draws through the canvas (circles, rings, lines, rectangles, oriented rectangles, triangles, bars, text, lights and shadow occluders, `sprite` for a material asset drawn as a textured quad with sheet uvs, `hud_image`/`hud_text`/`hud_text_width` for the interface layer in window pixels, and `pick` to declare where an entity can be clicked); `ctx->alpha` interpolates between ticks in the player, `ctx->editing` is set in the editor. `describe` optionally names entities for lists. Entities that only need a texture can skip drawing code altogether: the engine draws its `Sprite` component after the module's `draw`, and the interface (`cw_ui.h`) after that.
6. **Interface**: nothing to draw; a system reads `cw_game_ui_clicked(world, action)` for its buttons and writes `cw_ui_set_textf(world, &cw_game_world_of(world)->ui, id, ...)` into texts it finds by a component of its own (combat's `Scoreboard`).
7. **Metadata**: the name (stored in scenes and checked on load), a scene version, the tick rate and the level bounds. `CW_GAME_ABI_VERSION` in the table is checked on load, so a module built against an older engine is refused with a message instead of misread.

Hosts bind a world with `cw_game_world_init`, which runs the registrations and `bind`, then `cw_game_world_load_scene` / `save_scene`, `settle` (entity lifecycle without time), `tick`/`advance` (fixed step through `cw_clock`), `spawn` (a prefab) and `draw`. Loading a module: `cw_game_open` (shared library; the ABI version is checked) or `cw_game_use` (linked in).

## Scenes

A scene (`*.cwscene`) is the world written through reflection; a prefab (`*.cwprefab`) is the same format without allocator state, holding a fragment that `cw_scene_instantiate` copies into a live world with fresh ids (`cw_scene_write_entities` writes one from a list of entities). A scene, one indented line per component, enums and flags by label, strings quoted (`UiText text="press start"`, with `\"` and `\\` escapes), entity ids preserved so references between entities are plain ids, with optional display names:

```
cwscene 1
game combat 1
tick 0
next_id 23

entity 2 "center pillar"
  Position x=600 y=400
  Obstacle radius=34
  ShadowCaster

entity 11
  Position x=160 y=130
  Health current=120 maximum=120
  Attack damage=12 range=30 cooldown=0.800000012 timer=0 kills=0
  Unit team=red kind=melee
  Body radius=12 speed=90
  ShadowCaster
```

Loading requires a fresh world; a missing field takes the type's default, an unknown field is a counted warning, an unknown component is an error unless `ignore_unknown_components` is set, a value outside its range or a failed `validate` is an error, and any error resets the world. Transient components are never written. Binary snapshots (`cw_snapshot_*`, `clockwork.h`) remain the runtime format for saved games and use the same reflection through the generic codec.

## The games

Project files (`*.cwproj`) name the module, its sources, the scenes directory and main scene, the rendering settings file (`render`), the asset manifest, the player's `window` size and `title`, and the interface's reference resolution and scale mode (`ui`); `cw_project_save` writes them back, which is how the editor's project panel persists the window and interface settings.

**combat** (`games/combat`): a two-team battle. Units (melee, archer, tank) carry `Position`, `Velocity`, `HealthConfig` (config, baked into the runtime `Health`), `Attack`, `Unit`, `Body` and the `ShadowCaster` tag; `Target` and `Visual` are transient. Lights are entities (`Light` with colour, intensity, radius, falloff, volumetric strength, spot/no_shadows flags, direction, cone, flicker; transient `LightState`), optionally with a `Lifetime` or an `Attached` component (a torch that follows its parent and dies with it); `Obstacle` entities are pillars that units walk around and that cast shadows. Systems: targeting, movement (approach, separation, obstacles, arena bounds), combat (damage through `cw_commands_update`, so hits accumulate when the phase's command buffer flushes), light animation, lifetimes, attachment, death, and EntityCreated/Destroyed hooks. Nothing is random, so a scene played twice is bit-identical and a loaded scene continues exactly like the saved one (checked by `tests/test_game.c`). Prefabs: red and blue melee/archer/tank, lantern, cool lamp, spotlight, green, base light, torch (attaches to the nearest unit), pillar. `scenes/arena.cwscene` is the level and `render.cfg` its look (lighting, fog, bloom, tone mapping); the scene's HUD is a bar stretched across the top with a `UiText` per team carrying the game's `Scoreboard` component, which the `scoreboard` system fills with the units alive and the kills.

**orbit** (`games/orbit`): a gravity sandbox with a different schema (`Body` with mass and a fixed flag, `Ship` with a hull, a transient `Trail`), its own prefabs (star, planet, moon, ship), 60 Hz, a 1600x1000 level, and no render file yet (it renders with the defaults until the settings panel saves one). The same editor and player binaries run it.

The previous monolithic combat demo (`examples/combat.c`, with its in-game editing panel, particle and effect juice and the tuning panel) has been split into the module, the player and the editor; the particle/effects systems stay in render2d and are not yet wired to modules through the canvas.

## Use

Include `clockwork.h` and link the static library, or compile the sources in `src` into your program. CMake consumers can use `add_subdirectory` and link `clockwork::clockwork`. For a game, prefer the module route above (`cw_game.h`): it does steps 1, 2 and 5 for you and gives the editor and the player a handle on the world. The `examples/movement.c`, `examples/save_load.c`, `examples/visualizer.c` and `tests/test_clockwork.c` programs referenced by earlier revisions are built and run by the scripts only when present in the tree.

1. Initialize a `cw_world` with `cw_world_init` and a `cw_sim` with `cw_sim_init`.
2. Reserve component IDs with `cw_comp_block`. Register ordinary types with `CW_REGISTER`, call `cw_comp_register` to supply a name, size, alignment, and cleanup callback, or `cw_reflect_register` with a `cw_type_info` to get reflection, the generic codec and editor support in one call.
3. Create entities with `cw_world_create_entity`. Set data with `cw_comp_set`, or add a component using `cw_comp_add` and its optional initializer.
4. Build a signature with `cw_mask`, then iterate using `cw_query_iter` and `cw_query_next`. Access registered slots through `CW_GET`.
5. Register systems with `cw_sim_register`. Set `authority` explicitly to `CW_HOST_ONLY` or `CW_SHARED`; a zero-initialized C descriptor uses `CW_SHARED`.
6. Call `cw_sim_tick`, or dispatch phases yourself. Call Init/Start/Stop/Shutdown explicitly when appropriate for your application.
7. To persist a world, give each saved component a codec (or allow raw copies), call `cw_snapshot_save` into a `cw_writer` (full state) or `cw_world_serialize` into an owned `cw_buffer` (visible state only), and later register the same component names in a fresh world and call `cw_snapshot_load` or `cw_world_deserialize`. `cw_snapshot_peek` inspects an image without a schema.
8. Destroy the simulation and world when finished.

## render2d: reusable 2D renderer

`render2d/render2d.h` and `render2d/render2d.c` are a self-contained 2D renderer for Sokol applications. It depends only on `sokol_app`, `sokol_gfx`, `sokol_gl` and `sokol_debugtext` (whose implementations live in one translation unit, `examples/sokol_impl.c`, compiled with `SOKOL_NO_ENTRY`); it knows nothing about Clockwork, so it can be reused by any program that draws shapes with ids. The build scripts produce `clockwork_render2d` (`libclockwork_render2d.a` / `clockwork_render2d.lib`; CMake target `clockwork::render2d`).

What it provides:

- **Window and resizing.** The canvas follows the window every frame, in logical pixels, with high-DPI framebuffers handled internally; mouse positions are reported in the same logical space. `r2d_viewport()` and `r2d_resized_this_frame()` let the application re-layout.
- **Camera.** `r2d_camera` is a plain value (world center, zoom in pixels per unit, limits, y orientation) with pure functions: world/screen transforms, pan by a screen delta, zoom about an anchor point, fit a world rectangle into the viewport or into a sub-area (for example, beside a side panel), and the visible world rectangle. The renderer keeps one current camera and optionally drives it: right/middle-drag pans, the wheel zooms about the cursor, arrow keys and/or WASD pan, +/- zoom and Home resets (`r2d_desc.camera_controls` and friends). Camera input is ignored while the mouse is over the UI.
- **Drawing** in world or screen space (`r2d_set_space`): filled and outlined circles, rings and arcs, rectangles, thick lines and polylines, convex polygons, oriented rectangles, an adaptive grid, progress bars and pixel-sized text anchored to either space. Everything is alpha-blended, off-screen shapes are culled, and screen-space drawing is always composited above world-space drawing (sokol-gl/debugtext layers); `R2D_SPACE_WORLD_OVERLAY` is a third space, world-positioned but drawn above the world's sprites (the editor's gizmos); `R2D_SPACE_HUD` is screen-positioned like screen space but drawn below it, with its own sprite batch under its shapes and text (a game's interface, under the host's panels). `r2d_draw_text_scaled` draws the pixel font at an absolute scale for HUD text.
- **Images, materials and sprites** (`r2d_image.h`, `r2d_material.h`, `r2d_sprite.h`): image decoding (PNG through a built-in inflate, TGA, PPM/PGM) into RGBA8, textures, data-only materials (texture name, effect, parameters, blend, sampling, tint, tiling) with a text format, and textured quads drawn with them in world or screen space (`r2d_draw_sprite`, `r2d_draw_sprite_screen`) through one uber shader with the built-in effects, or a custom GLSL fragment function compiled at run time (`r2d_shader_compile`, with the driver's log). Sprites batch per material state in transient vertex buffers and flush after the world's shapes and before the screen UI.
- **Picking and selection.** Shapes submitted with `r2d_pick_circle`/`r2d_pick_rect` and an application id can be queried by point (`r2d_pick_at`, topmost wins) or box (`r2d_pick_in_rect`). A sorted selection set (`r2d_select_*`, `r2d_selection_prune` for ids that died) and a selection controller (`r2d_selection_update`) implement click, shift/ctrl-click toggling, click on empty space to clear, marquee box selection, and dragging selected items with the world-space delta reported back so the application can move them.
- **Immediate-mode UI** in screen space: panels, labels, buttons, toggles and bars with a configurable style. Widgets register their rectangles so `r2d_mouse_over_ui()` can shield the world from clicks that belong to the UI.
- **Input** for the current frame: mouse position/delta/buttons with pressed/released edges, wheel, key down/pressed/released/typed (auto-repeat, with a per-frame count so slow frames lose none) and modifiers, the characters typed this frame (`r2d_chars`, for text fields), plus `r2d_dt()` and frame statistics.

Frame protocol from the sokol_app callbacks:

```c
init:    r2d_setup(&desc);             /* sg_setup included unless skip_gfx_setup */
event:   r2d_handle_event(event);
frame:   r2d_begin_frame();
         ... r2d_draw_* and r2d_pick_* in world space ...
         r2d_selection_update(&result, true);
         r2d_set_space(R2D_SPACE_SCREEN); ... r2d_ui_* ...
         r2d_end_frame();
cleanup: r2d_shutdown();
```

The pure parts (vectors, rectangles, colors, camera math) are `static inline` in the header and are covered by `tests/test_render2d.c`, which needs no window.

### Post-process stack (`render2d/r2d_post.h`, `tunable.cfg`)

With the stack active (the default; `r2d_desc.no_post_process` opts out) the renderer draws the scene into an offscreen target instead of the window: RGBA16F when the backend supports it (`post.hdr`), MSAA-resolved at the window's sample count. A chain of fullscreen passes then runs in the order given by `stack.order`, ping-ponging between two targets, with the last pass writing straight into the swapchain; the screen-space UI is composited on top afterwards so it stays crisp (`post.apply_to_ui` sends it through the chain instead). The passes:

| Pass | What it does | Tunables |
| --- | --- | --- |
| `lighting` | 2D lights with soft shadows, volumetric in-scatter and animated fog (see below) | `[lighting]` and `[fog]` sections |
| `bloom` | soft threshold, separable gaussian blur at reduced resolution, additive combine | threshold, soft_knee, intensity, radius, passes, downscale |
| `dof` | depth of field for a 2D scene: a blurred copy is mixed in by distance from a focus point (radial) or band (tilt-shift); the focus can follow a world point (`r2d_post_set_focus_world`) | shape, focus_x/y, focus_radius, falloff, blur_radius, blur_passes, max_blur |
| `motion_blur` | directional and radial blur from the camera's own pan and zoom between frames | strength, max_offset, zoom_strength, samples |
| `chromatic_aberration` | radial RGB separation growing from a center | strength, center_x/y, falloff |
| `tonemap` | exposure, none/reinhard/aces/filmic curve, saturation, contrast, brightness, gamma | operator, exposure, gamma, saturation, contrast, brightness |
| `vignette` | tint towards the edges | radius, softness, intensity, roundness, color_r/g/b |
| `shake` | trauma-driven camera shake of the whole image (noise offset and rotation, `r2d_post_shake` adds trauma) | max_offset, max_angle, frequency, decay, exponent |

### Lights, shadows, volumetric light and fog (`render2d/r2d_lighting.h`)

The `lighting` pass (first in the default `stack.order`) lights the scene with 2D lights submitted every frame in world space (`r2d_light`: position, radius, color, intensity, falloff, optional spot cone, per-light volumetric strength, shadows on/off) against shadow casters submitted the same way (`r2d_light_occluder_circle` / `_segment` / `_rect` / `_polyline`). For each light the CPU builds a **polar shadow map** (the nearest occluder distance for every angle around the light; only the arc each occluder subtends is tested) and uploads one texture row per light; the GPU then renders every light additively into an HDR lightmap with two outputs: **direct light** at the surface, soft-shadowed with a five-tap penumbra, and **volumetric light**, the light integrated along the ray from the light to the pixel up to the first occluder, which makes shafts continue softly behind casters instead of stopping dead. The composite pass then computes `scene * (ambient + direct)` and blends it with **fog**: animated value-noise FBM in world space (so it scrolls with the camera and drifts with a wind vector) that is lit by ambient, direct and volumetric light, plus a `haze` amount of volumetric light that shows even where there is no fog. `[lighting]` (ambient color/intensity, global light and volumetric multipliers, haze, shadow softness, shadow map resolution, lightmap downscale, default falloff) and `[fog]` (density, color, feature scale, wind, contrast, octaves, ambient/direct response) are tunables like everything else; `r2d_lighting_get_stats` reports lights, casters, rays and the CPU time spent on shadow maps. The shadow map builder is pure and covered by the tests.

### Device tiers (`render2d/r2d_quality.h`, `[quality]`, `[tier_*]`)

Four tiers, `low`, `medium`, `high` and `ultra`, are budgets for what a device class may spend, stored as the `[tier_low]` .. `[tier_ultra]` sections of `tunable.cfg`: scene render scale, HDR targets, window MSAA (read before the window exists), bloom passes and downscale, whether depth of field and motion blur are allowed and how many passes/taps they get, whether lighting and fog are allowed, lightmap downscale, shadow map resolution, light count, fog octaves, and a particle multiplier that applications apply to their own particle counts and emitter rates (`r2d_post_particle_scale`). A tier never replaces the artistic settings: `r2d_tier_apply` clamps the cost knobs of the tuned parameters to the budget (fewer passes, larger downscales, fewer samples and rays, lower render scale, optional passes only where allowed) and leaves colors, thresholds and strengths alone, so a scene tuned on a high-end machine degrades gracefully. `[quality]` selects a tier or `auto`; with `auto` the renderer starts from what the device supports (`r2d_quality_pick_initial`: HDR support, framebuffer size) and, when `auto_adjust` is on, an adaptive controller lowers the tier after the smoothed frame time has stayed above the `target_fps` budget for about a second and raises it again after several seconds of headroom, with cooldowns and `min_tier`/`max_tier` bounds so it does not oscillate; stalls are not learnt. The stack reports the tier in effect, whether it was automatic, the smoothed frame time and the number of changes (`r2d_post_get_stats`, `r2d_post_current_tier`, `r2d_post_effective_params`), and `r2d_post_set_tier` forces one. The controller and the clamping are pure and unit-tested; the demo's status bar shows the tier, the panel has a tier cycle button, and the tuning panel exposes every tier table.

Everything is data driven: the parameters are a plain struct (`r2d_post_params`) described by a table of tunables (`render2d/r2d_tunables.h`: section, key, type, range, default, help), and `tunable.cfg` is that table in INI form. `r2d_post_load_config` reads it (also at setup through `r2d_desc.post_config`), `r2d_post_reload_if_changed` polls it so edits made while the program runs apply within half a second, `r2d_post_save_config` writes the current values back with their help comments and ranges, and the same table drove the former demo's tuning panel (a candidate for the editor's settings). `stack.order` lists the passes to run, first runs first; every pass also has its own `enabled` switch, and passes that would do nothing (no trauma, no camera motion, zero intensity) are skipped. The shader is one cross-backend program (GLSL 4.1, HLSL 5, MSL in `render2d/r2d_post_shaders.h`) selecting the pass kind from a uniform; `tests/test_r2d_post.c` covers the config layer headlessly (parsing, round trips, ranges, enums, hot-reload detection, order parsing, shake and motion math).

### Particle system (`render2d/r2d_particles.h`)

A particle system owns a fixed pool of particles and a table of emitters. Particles are spawned as one-shot bursts (`r2d_particles_burst`) or by emitters (`r2d_emitter_start`) that run for a duration or until stopped, can be moved every frame to follow an object (`r2d_emitter_move`, the emitted particles inherit its velocity), and can have their rate and direction changed. Every particle takes its behaviour from an `r2d_particle_desc`: lifetime, speed and direction cone, start/end size and color (with an alpha fade-in), gravity, drag, spin, spawn jitter, and shape (disc, spinning square, velocity-stretched streak, ring). `r2d_particles_update` advances the simulation with its own seeded random generator (deterministic), `r2d_particles_draw` renders in the renderer's current space; `r2d_particles_next` exposes live particles for custom rendering or tests. Emitter handles carry a generation so stale handles are ignored.

### Effects system (`render2d/r2d_effects.h`)

Timed visual effects driven by an eased 0..1 progress (`r2d_ease_apply`: linear, quadratic, cubic, back, elastic, bounce, pulse): floating text with drift, expanding rings (shockwaves), fading discs and beams, slash arcs that grow along a sweep, full-screen flashes, camera shake, and custom callbacks in either space. Effects return handles that can be moved (so they follow objects), re-colored or cancelled; a duration of zero loops the effect until cancelled, which is how persistent markers are made. `r2d_effects_draw(fx, space)` draws the world or screen layer, and `r2d_effects_camera_push`/`pop` apply the accumulated shake to the camera around the world pass. Both modules only touch the renderer when drawing, so `tests/test_r2d_fx.c` exercises their simulation headlessly with recording stubs for the draw calls.

## Behavioral contracts

Entity IDs are signed 64-bit integers with `-1` invalid. IDs are not recycled by default. Destroying an entity marks it immediately invisible to queries while keeping its data readable by ID through EntityDestroyed dispatch. The sweep then releases its components. Enabling `recycle_ids` allows stale IDs to alias new entities, as in Odin. Reset restarts IDs at zero and invalidates all old references.

`cw_world_restore_entity` returns true when it creates the requested ID. For an already active entity it cancels any pending destruction, preserves its data, and returns false. `cw_world_rebuild_entity` clears owned components, cancels pending destruction, and records a creation event while retaining the ID.

Created and pending-destruction views are borrowed arrays. The created list records creation events, so an entity created and destroyed in one tick may already be invalid when EntityCreated runs. EntityCreated runs after the sweep, then clears the creation list. Do not keep view pointers across world mutations. Creating entities during EntityCreated follows the original behavior: they join that same list, which is cleared after dispatch.

Every component pool reserves virtual address space for 16,777,216 slots by default and commits pages as capacity grows. This does not immediately consume that amount of physical memory. Define `CW_POOL_RESERVE_ENTITIES` when compiling the library to change the initial reservation. Component pointers remain stable while growth fits the reservation. Exceeding it relocates that pool and invalidates its old pointers. Removal, destruction, rebuilding, reset, and world destruction invalidate the affected logical component references. Entity-array pointers may change at every world capacity increase.

`CW_GET` checks registration, element size, and entity validity, but does not require component presence. Check `cw_comp_has` before reading a component that may be absent. Raw slot writes do not set presence; use `cw_comp_set` or `cw_comp_add`. Size checking cannot distinguish two C types with identical sizes. Invalid IDs and component IDs fail safely. Names are copied at registration.

`cw_comp_set` copies bytes and marks presence, without invoking initialization or cleanup. When replacing resource-owning values, release the previous resources yourself or remove the component first. `cw_comp_add` invokes initialization only when absent. Cleanup runs once on removal, rebuilding, sweep, reset, or destruction; a custom cleanup callback replaces default zeroing and must leave the slot reusable. Callbacks may release resources and edit their slot, but must not mutate the world or registry. Tags can be registered with size zero and alignment one. Component alignment must be a power of two no larger than the OS page size, and element size must be a multiple of alignment.

Queries require every component in the mask. An empty mask visits all visible entities. Marking/removing components during iteration is supported, including removal from another entity whose bit was already cached. Additions or restorations during an existing query are not guaranteed to appear; restart the query to observe them. Resetting or destroying a world during iteration is unsupported. Collect functions return the full result count and write at most the supplied output capacity; pass NULL/zero to measure.

System dispatch order is ascending `order`, then registration sequence. Named replacement retains its sequence and re-enables the system; unnamed systems are appended. Registration/removal during dispatch returns false. Enable/disable is permitted during dispatch and affects subsequent systems. Do not destroy the simulation while it is dispatching. Scheduler introspection pointers are borrowed and may change after sorting or registration. The scheduler does not step any physics library.

Pause gates EarlyUpdate, PhysicsUpdate, Update, LateUpdate, and EndFrame unless a system opts into `run_when_paused`. Lifecycle and user phases ignore pause. A tick still processes entity lifecycle and increments `world.tick` while paused. Client role skips host-only systems. Replay runs enabled shared Update systems regardless of pause.

Codec callbacks define the serialized format. Marshal takes a caller-owned buffer and reports required/written bytes through `size`; NULL/zero measures. Unmarshal writes a registered live slot and marks presence only on success. The callback must preserve the prior value on failure and handle any resource replacement. Missing callbacks return false; bytes are never silently treated as JSON. Transient is metadata for the snapshot save policy and does not disable explicit marshal calls.

`cw_writer` and `cw_reader` are the bounds-checked byte primitives behind snapshots, and codecs are encouraged to build on them: every multi-byte integer is little-endian, floats are IEEE-754 bit patterns, and signed values are two's complement. A growable writer never fails (allocation failure aborts); a fixed writer sets a sticky overflow flag, keeps counting the bytes required and never writes past its capacity; a NULL fixed writer only measures, which is exactly the marshal contract. A reader fails every access past its end, stores zero, leaves its position unchanged and sets a sticky error so a run of reads can be checked once. Size arithmetic is overflow-checked rather than wrapping, and `cw_reader_sub` bounds a length-prefixed span to its own reader.

Snapshots (`cw_snapshot_save`, `cw_snapshot_load`, `cw_snapshot_peek`) serialise a world into a versioned little-endian image whose layout is documented in `clockwork.h`: a magic/version/flags/size header, then tagged, length-prefixed sections for world state, the component schema, entity records and the recycled id list. Unknown sections are skipped so the format can grow; an unknown version or flag is rejected. The image holds every active entity, including those marked for destruction, its components, the tick, `next_id`, `recycle_ids`, the recycled list in order and `last_created`, so entity ids survive exactly and a loaded world allocates the same ids the saved world would have. Cached queries, observers, command buffers, the created list and the user pointer are not part of the image; the registry is not either, which is why the loading world must have registered the schema first. Components are matched by registered name, never by id, so registration order may differ between the saving and loading worlds.

A component is encoded by its marshal callback, or, without one and only with `allow_raw` in the save config, as the raw bytes of its slot; raw payloads are host layout, and the loader requires `allow_raw`, an identical element size and the same host byte order (recorded in the header flags). Without a codec and without `allow_raw` the save fails with `CW_SNAPSHOT_ERROR_NO_CODEC` naming the component. Transient components are skipped unless `include_transient` is set, and only components that some entity carries appear in the schema. A save appends to the caller's writer (growable, fixed, or measuring) and on failure truncates it back to its initial size; a fixed writer that is too small reports the bytes required in `error.offset`.

`cw_world_serialize` produces the same image format in a buffer the caller owns (`cw_buffer`, released with `cw_buffer_free`), but captures only the observable state: visible entities (active and not marked for destruction) with their ids, their non-transient components by registered name, the tick and `next_id`. Pending destructions, transient components, the recycled id list and `last_created` are omitted, and the image carries an empty recycled list; because `next_id` is kept, the omitted ids are never handed out again after a load. A snapshot of a world with nothing pending, no recycled ids and `last_created` cleared is byte-identical to its serialization. On failure nothing is allocated and the buffer is empty. The result loads and peeks like any snapshot.

`cw_world_deserialize` is the strict counterpart: it rebuilds a serialized image in a fresh world whose schema the caller has registered, resolving component types by name (registration order and ids may differ from the saving world), and restores entity ids, components, the tick and `next_id` exactly, so entities created afterwards get the ids the original world would have issued. Unknown component names and unsupported format versions are always rejected, and `check_user_version` additionally rejects a different application version. Failure never yields a half-built world: structure, limits and schema are validated before any entity exists, and if a codec rejects a payload later the entities built so far are released through the normal reset path (cleanup callbacks run, observers see the removals) and the world is fresh again with its prior settings; the call returns false in every such case.

The file helpers (`cw_snapshot_save_file`/`cw_snapshot_load_file`, `cw_world_serialize_file`/`cw_world_deserialize_file`, and the plain `cw_file_write`/`cw_file_read`) wrap these memory APIs with whole-file I/O and explicit ownership: paths, worlds and configs are borrowed for the call, and the buffer `cw_file_read` fills belongs to the caller until `cw_buffer_free`. A save encodes the complete image in memory first, writes it to a sibling temporary (`path.tmp`), flushes it to disk, and only then renames it over `path`, so neither an encoding failure nor an I/O failure can damage a valid file already there, and a crash mid-write leaves at most the temporary behind. A load reads the whole file (bounded by `max_size`, default `CW_FILE_DEFAULT_MAX_SIZE`) and then applies the memory API's guarantees. `cw_file_error` carries a file status, the `errno` captured at the failing call, and for `CW_FILE_ERROR_SNAPSHOT` the full `cw_snapshot_error`. The `examples/save_load.c` tool exercises all of this interactively and in its headless self-check.

A load requires a fresh world (a new or reset one: no entities, `next_id` zero, no recycled ids) and a load config; zero fields take `CW_SNAPSHOT_DEFAULT_*`, `cw_snapshot_load_defaults` spells them out, and `SIZE_MAX`/`INT64_MAX` mean unlimited. Every count, id and payload length is validated against `max_entities`, `max_entity_id` and `max_component_bytes`, and every schema entry against the registry, before the world is touched, so untrusted input cannot commit memory or reach a callback; the corruption checks also cover section structure, ascending unique ids, ids below `next_id`, duplicate components, unknown flags, and recycled ids that are live or repeated. Unknown component names fail with `CW_SNAPSHOT_ERROR_UNKNOWN_COMPONENT` unless `ignore_unknown_components` is set, in which case those payloads are skipped. Only a codec can still reject a payload during the apply phase; the world is then reset, so after any failure it is fresh again and `error` reports the status, byte offset, entity and component involved. Loaded entities are reported in `cw_world_created` like restored ones, so EntityCreated systems can rebuild transient state, and pending destructions are re-marked. Trailing bytes after an image are an error; `cw_snapshot_peek` reports an image's size and header fields for callers embedding snapshots in larger streams.

The API is single-threaded. Worlds and simulations must be initialized once and destroyed before reuse; copying initialized objects by value is unsupported. Allocation failure and size overflow abort, matching the source implementation's fatal allocation policy. Invalid negative or non-finite frame times are ignored. No external allocator, thread scheduler, or dependency graph is introduced.
